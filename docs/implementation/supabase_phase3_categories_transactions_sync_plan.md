# Supabase Phase 3 Categories + One-Time Transactions Sync Plan

## 1. Purpose

This document is a **planning document only** for BudgetMeter Phase 3 Supabase sync of:

- financial categories (seeded + custom + recurring configuration rows)
- one-time income entries
- one-time expense entries

It does **not**:

- implement Swift sync
- create Supabase migrations or SQL
- modify Supabase Edge Functions
- modify Core Data schema
- change app runtime behavior
- alter Phase 1 account/settings integration
- alter Phase 2B `savings_goals` implementation or spec work

The goal is to define a safe architecture **before** any Phase 3 implementation begins.

Related broader context lives in:

- `docs/implementation/supabase_phase1_migration_spec.md` (account/settings — done/in progress)
- `docs/implementation/supabase_phase2b_savings_goals_migration_spec.md` (first financial sync candidate)
- `docs/implementation/supabase_phase2_financial_sync_plan.md` (full financial roadmap; Phase 3 here corresponds to that doc’s Phase 2F slice)

## 2. Current State

### 2.1 Single overloaded local entity

BudgetMeter stores income categories, expense categories, custom categories, recurring pace configuration, and one-time income/expense entries in **one Core Data entity**:

- Entity: `FinancialCategory`
- Source: `budgetmeter.ios/BudgetMeter.xcdatamodeld/BudgetMeter 3.xcdatamodel/contents`

There is **no separate transaction entity**. One-time entries are not category-like rows in a different table — they are `FinancialCategory` rows with `entryKind = "oneTime"`.

There are also **no declared Core Data relationships** between financial entities. Links are logical only (string fields like `uniqueID`, `sourceType`, `sourceID`).

### 2.2 How income categories are stored

- All income rows are `FinancialCategory` with `type == "income"`.
- Loaded in `IncomeViewModel.loadIncomeCategories()`:
  - recurring rows filtered by `FinancialCategoryWriteSupport.isRecurringDisplayCategory(_:)`
  - grouped by `frequency` (`daily`, `weekly`, `monthly`, `yearly`)
  - one-time rows filtered by `FinancialCategoryWriteSupport.isOneTimeDisplayCategory(_:)`
- Recurring income “categories” are configuration rows: each row holds an `amount` representing the user’s recurring pace for that category slot.
- Display name comes from:
  - `customName` if `isCustom == true`
  - localized `uniqueID` via `DataSeedingService.displayName(for:)` otherwise

### 2.3 How expense categories are stored

Same pattern as income, via `ExpenseViewModel.loadExpenseCategories()` with `type == "expense"`.

Expense view also shows subscriptions from a separate `Subscription` entity, but subscription amounts are **not** stored inside `FinancialCategory` for those rows.

### 2.4 How custom categories are stored

Custom categories are still `FinancialCategory` rows with:

- `isCustom = true`
- `customName` (user-entered display name)
- `customIconName`, optional `customColorHex` (premium-gated color)
- `uniqueID = "custom_<uuid>"` assigned in `CategoryValidationService.createCustomCategory(...)`
- `entryKind` set by `FinancialCategoryWriteSupport.applyMetadata(...)`:
  - `.recurring` for recurring custom categories
  - `.oneTime` for one-time custom categories

Creation path: `CreateCategoryModal` → `CategoryValidationService`.

Deletion: only custom rows can be deleted (`IncomeViewModel.deleteCategory`, `ExpenseViewModel.deleteCategory`, `CategoryValidationService.deleteCustomCategory`). Seeded rows cannot be deleted.

Duplicate protection: normalized display-name comparison against both custom names and localized seeded names (`CategoryValidationService.categoryExistsNormalized(...)`).

### 2.5 How one-time income entries are stored

One-time income entries are `FinancialCategory` rows where:

- `type == "income"`
- `entryKind == "oneTime"` (or legacy `frequency == "once"`)
- `occurrenceDate` set
- `amount` holds the one-time value
- typically `isCustom == true` (created via `CreateCategoryModal` with `entryIntent: .oneTime`)

They appear in the “One-Time Income” section in `IncomeView`. Each entry is its own row — not an append-only list attached to a parent category.

Some one-time rows may also be generated by recurring automation (`sourceType = "recurringAutomation"`, `sourceID` pointing at a `RecurringTransaction` UUID). Those are logically one-time history rows but originate outside manual user entry.

### 2.6 How one-time expense entries are stored

Same as one-time income, with `type == "expense"`. Shown in the “Surprise Expenses” section in `ExpenseView`.

### 2.7 Seeded vs user-created categories

| Aspect | Seeded (default) | Custom (user-created) |
|---|---|---|
| Created by | `DataSeedingService.seedPredefinedCategories()` on first launch | `CategoryValidationService.createCustomCategory(...)` |
| `isCustom` | `false` (default) | `true` |
| Stable key | `uniqueID` (e.g. `food`, `rent`, `monthly_salary`) | `uniqueID = custom_<uuid>` |
| Display name | **Not stored** in Core Data; resolved from `Categories.xcstrings` via `category.<uniqueID>.name` | Stored in `customName` |
| Icon/color | Hard-coded maps in `DataSeedingService.sfSymbolName(for:)` | `customIconName`, optional `customColorHex` |
| Local `id` | new `UUID()` per install row | new `UUID()` at creation |
| Deletable | No | Yes (if custom) |
| Count (current seed) | ~58 rows per fresh install (daily/monthly/yearly; no seeded weekly rows) | Variable |

Legacy installs may have old `uniqueID` values; `DataSeedingService.migrateOldCategoryIDsIfNeeded()` maps Turkish/legacy IDs to canonical keys.

### 2.8 Do categories and transactions share the same entity?

**Yes.** Locally, both recurring category configuration and one-time entries live in `FinancialCategory`.

For Supabase Phase 3, this local overload is the primary reason to **split remote tables** even though Core Data remains unchanged in Phase 3 planning.

### 2.9 Related but out-of-scope entities (must not block Phase 3 design)

These exist locally and reference categories as strings or generate one-time rows, but are **not Phase 3 implementation scope**:

- `RecurringTransaction` — separate entity; automation creates one-time `FinancialCategory` rows
- `Subscription`, `Bill`, `BillPayment` — category stored as string label
- `FinancialSnapshot` — derived analytics snapshots
- `SavingsGoal` — Phase 2B sync candidate; independent table

Phase 3 must not interfere with Phase 2B `savings_goals` work.

## 4. Main Risk Analysis

Phase 3 is materially harder than `savings_goals` (Phase 2B) because:

### 4.1 One entity, multiple meanings

`FinancialCategory` simultaneously represents:

1. seeded recurring budget slots
2. custom recurring categories
3. one-time income/expense events
4. automation-generated one-time history rows

`savings_goals` is a single-purpose entity with clear fields and no seeded catalog.

### 4.2 Recurring config is mixed into category rows

There is no separate “category definition” vs “budget amount” split locally. A seeded row like `food` **is** the recurring configuration row (`amount` = daily food budget).

Remote sync must decide whether to sync:

- only non-zero/user-touched seeded rows, or
- all seeded slots including zero defaults

### 4.3 One-time entries are category-shaped rows, not normalized transactions

One-time entries reuse the category entity. They carry category metadata (`customName`, icon) inline rather than referencing a separate category row.

### 4.4 Duplicate category risks

| Risk | Cause |
|---|---|
| Seeded duplicate rows across devices | each install creates ~58 rows with different random `id` UUIDs but same `uniqueID` |
| Seeded + remote seeded both applied | bootstrap pulls remote rows while local seed also runs |
| Custom duplicate names | possible across devices if created independently with same display name |
| Backup restore + sync merge | `RestoreImporter` inserts rows without dedupe against Supabase |
| Legacy `uniqueID` drift | old installs may still have pre-migration keys until migration runs |

### 4.5 Localization risks

Seeded category display names are **not persisted** — they come from localized string catalogs (`Categories.xcstrings`). Syncing display names for seeded categories would:

- bloat remote storage
- create language-mismatch across devices
- fight the current localization architecture

Remote schema should store **template keys**, not localized labels, for seeded categories.

### 4.6 Category identity problems across devices

Current backup identity (`BackupSerializer.clientRecordID(for:fallback:)`) prefers local `id.uuidString`. That works on the same device / backup-restore path but **fails cross-device** for seeded rows because each device generates different UUIDs for the same `uniqueID`.

### 4.7 Delete semantics are immature for sync

- Custom categories: hard delete (`context.delete`)
- Seeded categories: not deletable
- `isActive` exists but is not used as a universal soft-delete/tombstone flag in UI flows
- No `deleted_at` locally

Phase 3 requires remote tombstones and a local sync-state layer before mirroring deletes safely.

### 4.8 Interaction with recurring automation (future concern)

`RecurringTransaction` processing creates one-time `FinancialCategory` rows with `sourceType/sourceID`. Phase 3 can sync those rows, but full correctness depends on Phase 2E `recurring_transactions` sync being stable. Phase 3 MVP should treat `source_type/source_client_record_id` as optional metadata, not hard FK initially.

## 5. Recommended Data Model

### Recommendation: split into separate Supabase tables

Do **not** mirror the local overloaded `FinancialCategory` as one remote table.

Recommended Phase 3 tables:

1. `financial_categories` — recurring category configuration (seeded overrides + custom recurring categories)
2. `one_time_transactions` — one-time income/expense entries
3. **No** `category_templates` table in MVP — use app-bundled seed catalog + `category_key`
4. **Defer** `recurring_transactions` to later phase (not Phase 3 scope)

Optional future table (not Phase 3):

- `category_templates` — only if server-driven category catalog becomes a product requirement

---

### 5.1 `financial_categories`

**Purpose:** Persist account-owned recurring category configuration that should survive across devices.

**Include:**

- custom recurring categories (`is_custom = true`)
- user-modified seeded recurring slots (non-zero amount and/or user metadata changes)

**Exclude from initial upload:**

- all untouched zero-amount seeded rows (recreated locally from app seed catalog)

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | server row id |
| `user_id` | `uuid` FK → `auth.users` | owner |
| `client_record_id` | `text` not null | stable client identity |
| `category_key` | `text` null | seeded template key (`food`, `rent`); null for pure custom rows |
| `type` | `text` not null | `income` / `expense` |
| `frequency` | `text` not null | `daily`, `weekly`, `monthly`, `yearly` |
| `amount` | `numeric` not null default 0 | recurring pace amount |
| `is_custom` | `boolean` not null default false | |
| `custom_name` | `text` null | required when `is_custom=true` |
| `custom_icon_name` | `text` null | |
| `custom_color_hex` | `text` null | |
| `is_active` | `boolean` not null default true | |
| `created_at` | `timestamptz` not null | |
| `updated_at` | `timestamptz` not null | |
| `deleted_at` | `timestamptz` null | soft delete tombstone |

**Ownership:** `user_id = auth.uid()` on all mutations.

**Unique constraints:**

- `(user_id, client_record_id)` — required
- optional partial unique for seeded rows after rules finalized:
  - `(user_id, category_key, type, frequency) WHERE category_key IS NOT NULL AND deleted_at IS NULL`

**Indexes:**

- `(user_id, updated_at DESC)`
- `(user_id, deleted_at)`
- `(user_id, type)`
- `(user_id, is_custom)`
- `(user_id, category_key)`
- `(user_id, type, frequency)`

**RLS:**

- authenticated owner-only SELECT/INSERT/UPDATE
- DELETE optional (prefer soft delete via `deleted_at`)

## 7. Identity Strategy

### 7.1 Default / seeded categories

**Do not sync full seeded catalog rows in Phase 3 MVP.**

Instead:

- local seed catalog remains authoritative for template existence
- remote stores only **user state overrides** for seeded slots

Stable seeded identity key (logical):

```text
seed:<type>:<category_key>:<frequency>
```

Recommended `client_record_id` for seeded override rows:

```text
seed:<type>:<category_key>:<frequency>
```

This is stable across devices and independent of local Core Data `id`.

### 7.2 Custom categories

Use existing local `FinancialCategory.id.uuidString` as `client_record_id` when present.

If legacy migrated rows lack `id`, assign one during migration/bootstrap before first upload.

Do **not** rely on `uniqueID = custom_<uuid>` alone — treat it as auxiliary metadata.

### 7.3 One-time income/expense entries

Use local row `id.uuidString` as `client_record_id`.

Each one-time entry is its own record; duplicates are prevented by `(user_id, client_record_id)`.

For automation-generated rows:

- keep `source_type = recurringAutomation`
- map `sourceID` → `source_client_record_id` using recurring transaction client identity (when that phase exists)

### 7.4 Are existing local UUIDs reliable?

| Row type | Local `id` reliable cross-device? |
|---|---|
| Custom recurring category | **Yes** (if created on one device and synced before duplicate creation elsewhere) |
| One-time entry | **Yes** as `client_record_id` once synced |
| Seeded recurring slot | **No** — must use derived seed key |
| Legacy migrated custom rows missing `id` | **No** until backfilled |

### 7.5 New local fields required later (implementation phase, not now)

Future Swift work will need per-record sync metadata (likely without Core Data schema change in planning stage, but realistically requiring a migration later):

- `clientRecordID` (explicit persisted stable id)
- `remoteUpdatedAt`
- `syncStatus`
- `deletedAt` mirror

Planning assumption: Phase 3 implementation will add sync metadata through a deliberate Core Data migration **after** this spec is approved — that migration is out of scope for this document’s “no Core Data changes” constraint during planning.

### 7.6 Duplicate prevention across devices

1. Upsert match on `(user_id, client_record_id)` always.
2. For seeded overrides, upsert match on `(user_id, category_key, type, frequency)` as secondary safety.
3. Never upload full seeded catalog on first sign-in.
4. On pull, apply remote custom rows by `client_record_id`; apply seeded overrides by seed key mapping to local seeded slot.

## 8. Seeded Categories Strategy

### Options analyzed

| Option | Description | Pros | Cons |
|---|---|---|---|
| A | Do not sync seeded categories; recreate locally | simplest; zero duplication | no cross-device amount sync for seeded slots |
| B | Sync only custom categories | avoids seeded duplication | seeded slot amounts still device-local |
| C | Sync all categories including seeded defaults | complete remote mirror | ~58 duplicate rows/user; high conflict noise |
| D | Store template keys only; sync overrides | stable identity; minimal rows | requires mapping layer |

### Recommended approach: **D (template keys + override sync), with A locally**

Safest Phase 3 MVP:

1. **Local seed catalog always recreated** on fresh install (`DataSeedingService`).
2. **Remote stores only**:
   - custom categories (`is_custom=true`)
   - seeded slot **overrides** where user changed `amount` or active state
3. **Do not upload** untouched zero-amount seeded rows.
4. **Do not store localized display names** for seeded templates remotely.

This is strictly safer than option C and more useful than option B alone.

## 9. One-Time Entry Strategy

### 9.1 Should entries reference category rows?

**MVP recommendation:** soft reference, not hard FK.

Store on `one_time_transactions`:

- `category_key` nullable (when entry maps to a seeded/custom template)
- `category_label` required (denormalized snapshot)
- optional icon/color metadata

Reason: one-time entries are often free-form custom names and must remain readable even if the category is deleted later.

### 9.2 Category rename/delete behavior

| Event | Desired behavior |
|---|---|
| Custom category renamed | existing one-time rows keep original `category_label` snapshot |
| Custom category deleted | one-time history remains visible with snapshot label |
| Seeded slot amount changed | does not rewrite historical one-time labels |
| Automation-generated row | preserve `source_type/source_client_record_id` for traceability |

### 9.3 Required reference fields

Phase 3 MVP should include **all** of:

- `category_key` (nullable, for template linkage/analytics)
- `category_label` (required, for UI/history stability)
- not a hard FK to `financial_categories.id` in MVP

## 10. Delete / Archive Strategy

### 10.1 Remote delete model

Use **soft delete** with `deleted_at` on both Phase 3 tables.

Hard delete only during account deletion cleanup (server-side admin delete in `delete-account` Edge Function).

### 10.2 Category deletion behavior

| Category type | Local today | Phase 3 target |
|---|---|---|
| Custom recurring category | hard delete | set `deleted_at` remotely; tombstone pull removes/hides locally |
| Seeded recurring slot | not deletable | represent “reset” as override row delete or amount=0 override; do not delete template |
| One-time entry | deletable if custom | soft delete tombstone in `one_time_transactions` |

### 10.3 Transaction deletion behavior

- User delete → local remove + remote `deleted_at`
- Pull sees tombstone → remove/hide local row even if previously synced

### 10.4 Tombstone retention

Keep tombstones through incremental sync window (recommended ≥ 30 days) or until full sync checkpoint — exact retention TBD before SQL migration.

### 10.5 Account deletion

Hard delete all user-owned rows in Phase 3 tables by `user_id` during account deletion (future Edge Function update).

## 11. Offline Sync Strategy

Future Phase 3 runtime behavior (not implemented in this planning doc):

1. **Local write first** — preserve current UX; Core Data remains immediate source of truth.
2. **Mark pending sync** — per-record dirty state when financial sync is enabled and user is signed in.
3. **Upload when online** — upsert changed rows to Supabase.
4. **Pull remote changes** — since last sync watermark (`updated_at` cursor per table).
5. **Apply pulled rows** — map to local seeded slots / custom rows / one-time list.
6. **Avoid duplicates** — match by `client_record_id` and seeded seed keys.
7. **Handle tombstones** — honor remote `deleted_at` locally.

### Bootstrap on sign-in (future)

1. Ensure local seed catalog exists.
2. Pull remote `financial_categories` + `one_time_transactions`.
3. Merge:
   - custom categories by `client_record_id`
   - seeded overrides by seed key
   - one-time entries by `client_record_id`
4. Do **not** block app launch on failure (same pattern as Phase 1 account settings).

### Phase 1 pattern reuse

Phase 1 `SupabaseAccountDataService` uses lightweight last-write-wins with local mutation timestamps. Phase 3 requires **per-record** pending state — UserDefaults keys are insufficient.

## 12. Conflict Resolution

### MVP rules

| Data | Rule |
|---|---|
| Category metadata (custom name/icon/color) | last-write-wins by server `updated_at` |
| Seeded override amount | last-write-wins by server `updated_at` |
| One-time transaction amount/date/label | last-write-wins by server `updated_at` |
| Deletes | `deleted_at` tombstone wins over non-deleted stale payload |
| Seeded template conflicts | avoided entirely — templates are local catalog, not synced rows |
| Simultaneous create same seed key | merge by `(user_id, category_key, type, frequency)` unique guard |

### Explicit non-goals for Phase 3 MVP

- no field-level merge
- no CRDT
- no silent destructive merge of one-time history
- no auto-deduplication by display name across devices

## 13. RLS / Security

### Requirements

1. Every user-owned table includes `user_id` referencing `auth.users(id)`.
2. RLS enabled on all Phase 3 tables.
3. Policies:
   - SELECT/INSERT/UPDATE for `authenticated` where `auth.uid() = user_id`
   - UPDATE must include both `USING` and `WITH CHECK` (Postgres UPDATE needs SELECT policy)
4. No anonymous access to user financial rows.
5. Client uses anon key only; never service role in app.
6. User cannot attach rows to another user’s `user_id` — enforced by policy + optional trigger guard.
7. Cross-table ownership: if hard FKs are added later, policies/triggers must verify referenced category belongs to same `user_id`.

### Optional hardening (pre-SQL decision)

- `before insert/update` trigger to force `user_id = auth.uid()`
- prevent mutating `user_id` on update

## 14. Index / Performance Plan

### Required indexes (both tables)

- unique `(user_id, client_record_id)`
- `(user_id, updated_at DESC)` — incremental pull
- `(user_id, deleted_at)` — tombstone queries

### `financial_categories` additional indexes

- `(user_id, type)`
- `(user_id, is_custom)`
- `(user_id, category_key)`
- `(user_id, type, frequency)`
- partial unique on seeded keys (optional, see §5.1)

### `one_time_transactions` additional indexes

- `(user_id, occurrence_date DESC)`
- `(user_id, type, occurrence_date DESC)`
- `(user_id, category_key)`

### Query patterns to optimize

- pull changes since cursor: `updated_at > :cursor`
- fetch recent one-time history for insights: `occurrence_date` range scans
- list active custom categories: `is_custom=true AND deleted_at IS NULL`

## 15. Migration Strategy

Phase 3 first-sync migration (future implementation) should handle:

### 15.1 Local → remote initial upload

| Local source | Remote target | Rule |
|---|---|---|
| Custom recurring categories | `financial_categories` | upload all active custom rows |
| Seeded rows with non-zero amount | `financial_categories` | upload as seed-key overrides only |
| Seeded rows amount=0 untouched | none | skip |
| One-time rows (`entryKind=oneTime`) | `one_time_transactions` | upload all active/historical entries |

Assign `client_record_id` using §7 rules before upload.

### 15.2 Remote-empty / local-existing (new sign-in on device with data)

1. Seed local catalog if missing.
2. Upload local custom + overrides + one-time entries.
3. Mark synced.

### 15.3 Remote-existing / local-empty (reinstall)

1. Run local seed catalog.
2. Pull remote rows.
3. Apply overrides onto seeded slots; insert custom + one-time rows.

### 15.4 Both exist (overlap)

1. Seed local catalog.
2. Pull remote updated since cursor.
3. Merge by `client_record_id` and seed keys.
4. Last-write-wins using `updated_at`.
5. Upload local-only rows still pending.

### 15.5 Duplicate prevention during migration

- never insert a second local seeded row for same `(type, category_key, frequency)`
- if local seeded row exists, update amount/metadata instead of insert
- skip uploading full seeded catalog

### 15.6 BackupService coexistence

Manual backup/restore remains available during Phase 3 rollout. Structured sync must not assume backup payloads are absent. Sync identity rules in this doc supersede backup `clientRecordID` behavior for cross-device structured sync.

## 19. Risks / Open Questions

Must be decided **before** SQL migration:

1. **Weekly seeded slots:** UI supports weekly custom categories, but seed catalog does not. Should Phase 3 support weekly seeded overrides or custom-only weekly?
2. **Zero-amount seeded overrides:** if user sets a seeded slot to 0 remotely, is that an override row or delete of override?
3. **Legacy rows with `uniqueID=nil`:** strict backfill policy before first upload?
4. **Automation-generated one-time rows:** include in Phase 3 MVP or manual entries only?
5. **Currency per row:** add nullable `currency_code` now or defer until multi-currency rows exist locally?
6. **Tombstone retention window:** how long must deleted rows remain pullable?
7. **Core Data sync metadata migration:** when/how to add `clientRecordID`/sync fields without breaking CloudKit container?
8. **Premium-gated custom color sync:** sync `custom_color_hex` for all users or gate at UI only?
9. **Duplicate custom names across devices:** block, merge, or allow duplicates with distinct `client_record_id`?
10. **Conflict UI:** silent last-write-wins vs surfacing sync conflicts to user?
11. **Initial sync trigger:** on sign-in only, manual “Sync now”, or background periodic sync?
12. **Relationship to CloudKit:** continue parallel CloudKit Core Data sync during transition or disable for synced entities?

## 20. Final Recommendation

### Recommended Phase 3 table structure

1. `financial_categories` — custom recurring categories + seeded slot overrides only
2. `one_time_transactions` — all one-time income/expense entries

Do **not** create `category_templates` or sync full seeded catalogs in Phase 3 MVP.

### Safest first implementation slice

Implement in this order:

1. **Schema + RLS + delete-account plan** (SQL migration after spec approval — not now)
2. **One-time transactions sync only** (`one_time_transactions`)
   - simplest identity (`id.uuidString`)
   - no seeded-key merge complexity
   - immediate user value for history across devices
3. **Custom recurring categories sync** (`financial_categories`, `is_custom=true`)
4. **Seeded override sync** (`financial_categories` with seed-key `client_record_id`)
5. Tombstones + offline retry queue hardening

### What should be implemented first

**Start with `one_time_transactions`**, not recurring category configuration.

Reason: one-time entries have stable UUID identity, no seeded catalog duplication, and fewer localization/template edge cases — while still delivering meaningful cross-device financial history sync.

### What must not be touched yet

- Phase 1 account/settings Swift integration (`SupabaseAccountDataService` for profiles/settings/notifications)
- Phase 2B `savings_goals` spec/implementation
- Core Data schema changes (until approved follow-up migration spec)
- `BackupService` removal
- CloudKit removal
- `RecurringTransaction` structured sync
- subscriptions, bills, snapshots
- paywall / StoreKit logic
- UI redesign

### Review recommendation

This plan should be reviewed by:

1. **Cursor agent** for codebase alignment (local entity inspection, file path accuracy)
2. **Codex or stronger model** for second-pass review focused on:
   - seeded identity edge cases
   - migration/conflict safety
   - RLS/policy completeness
   - cross-device duplicate scenarios

Do not begin SQL migrations or Swift sync services until open questions in §19 are resolved and Phase 2B savings sync is stable in production QA.

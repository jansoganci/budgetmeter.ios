# Phase 7 Premium Cleanup Gap Analysis

## Executive summary

Phase 7's premium matrix marks both `BudgetMeterCapability.subscriptionTracking` and `BudgetMeterCapability.recurringAutomation` as `.premium`, but enforcement is incomplete.

- `subscriptionTracking` is an actual UI/service exposure: free users can see the Expense screen subscriptions section, open existing subscriptions, and launch the add-subscription flow.
- `recurringAutomation` is an actual automation exposure: free users with active `RecurringTransaction` records can have due transactions generated by app refresh/background processing. There is also a related manual refresh path in `RecurringTransactionsViewModel` that should be reviewed because it performs the same automation.

The matrix behavior is in `budgetmeter.ios/CoreKit/Sources/Premium/PremiumManager.swift`: `PremiumManager.hasAccess(to:)` returns `true` for `.free`, `isPremium` for `.premium`, and `false` for `.postponed` (lines 54-67). The capability matrix marks `subscriptionTracking` and `recurringAutomation` as `.premium` (lines 352-405), and `PremiumFeature.subscriptionTracking` / `.recurringTransactions` map to those capabilities (lines 415-449).

## Gap 1: `subscriptionTracking` - Expense screen subscriptions section

### Missing gate

File: `budgetmeter.ios/Features/ExpensesFeature/View/ExpenseView.swift`

- Lines 14-15: `ExpenseView` owns only `ExpenseViewModel` and `LocalizationManager`; it does not observe `PremiumManager`.
- Lines 71-72: the `subscriptionsSection` is always rendered between Monthly and Yearly expense sections.
- Lines 202-239: `subscriptionsSection` always builds the full `FinancialSection`.
- Lines 211-218: existing subscriptions are rendered with editable `SubscriptionRowView` rows.
- Lines 233-236: `AddSubscriptionRow` always opens the add-subscription sheet by setting `showingAddSubscription = true`.
- Lines 123-131: both subscription add/edit sheets are always available when the state variables are set.

File: `budgetmeter.ios/Features/ExpensesFeature/ViewModel/ExpenseViewModel.swift`

- Lines 23, 35-45, 56-60, 192-195, 221-230: subscription data and totals are loaded and exposed without checking `PremiumManager`.
- Lines 89-100: `init` calls `loadSubscriptions()` immediately for every user.
- Lines 187-190: `refresh()` calls `loadSubscriptions()` for every user.

### Impact

This is not theoretical. Free users can reach and use subscription tracking from the Expense tab because `ExpenseView` is mounted directly in `ContentView` without a premium wrapper (`budgetmeter.ios/ContentView.swift`, lines 35-40). The section is visible, rows are tappable, and the add-subscription flow is reachable. The view model also includes subscription count in `activeSourcesCount`, so subscriptions affect the summary card source count for free users.

Financial totals are more nuanced: `ExpenseViewModel.totalMonthlyExpenses` uses `FinancialSummaryBuilder`, and that builder may include subscriptions in recurring expense totals independently of this section. The UI gap still exposes the subscription management feature itself to free users.

### Fix approach

Use the existing view-level premium gate pattern:

- Add `@StateObject private var premiumManager = PremiumManager.shared`.
- Add `@State private var showingSubscriptionPaywall = false`.
- Replace the always-rendered `subscriptionsSection` call at lines 71-72 with a gate:
  - If `premiumManager.hasAccess(to: BudgetMeterCapability.subscriptionTracking)`, show `subscriptionsSection`.
  - Otherwise show a locked section/upgrade affordance, or wrap the section in `PremiumFeatureView(premiumFeature: .subscriptionTracking) { subscriptionsSection }` if a full replacement view is acceptable.
- Add `.sheet(isPresented: $showingSubscriptionPaywall)` with `PremiumPaywallView(feature: .subscriptionTracking, ...)`, matching existing patterns in `SavingsGoalsView` lines 19-20 and 64-69, and `CreateCategoryModal` lines 266-314.
- Guard direct actions as well:
  - In `AddSubscriptionRow`, only set `showingAddSubscription = true` when `premiumManager.hasAccess(to: BudgetMeterCapability.subscriptionTracking)`; otherwise set `showingSubscriptionPaywall = true`.
  - In row taps, either block editing for free users or avoid rendering subscription rows when locked.

Recommended additional hardening:

- Gate `ExpenseViewModel.loadSubscriptions()` or inject premium state so non-premium users do not load subscription rows/totals for this screen.
- Decide whether the summary builder should include subscription costs for free users. If the product intends subscription tracking to be premium, but recurring expense totals may still include already-stored subscriptions, this needs an explicit product decision.

## Gap 2: `recurringAutomation` - BackgroundProcessingService

### Missing gate

File: `budgetmeter.ios/CoreKit/Sources/Background/BackgroundProcessingService.swift`

- Lines 58-64: `handleBackgroundTask(_:)` always calls `await processRecurringTransactions()` before snapshots and notifications.
- Lines 67-112: `processRecurringTransactions()` fetches every active `RecurringTransaction` and processes due or overdue entries without checking premium status.
- Lines 92-100: due transactions are converted into actual transactions and advanced to the next due date.
- Lines 114-124: `createTransactionFromRecurring(_:context:)` creates a `FinancialCategory` entry without checking premium status.
- Lines 197-202: `applicationWillEnterForeground()` also calls `await processRecurringTransactions()` whenever the app becomes active.

Related path:

File: `budgetmeter.ios/Features/RecurringTransactionsFeature/ViewModel/RecurringTransactionsViewModel.swift`

- Lines 184-215: `processDueTransactions()` manually performs the same due-recurring automation without a premium check.
- Lines 217-238: its `createTransactionFromRecurring(_:)` creates a one-time `FinancialCategory` with `sourceType: "recurringAutomation"`.

File: `budgetmeter.ios/Features/RecurringTransactionsFeature/View/RecurringTransactionsView.swift`

- Lines 94-96: `.refreshable` triggers `await viewModel.processDueTransactions()`.

### Impact

This is an actual feature leak for users who have active recurring transaction records. The background service is scheduled at app launch (`budgetmeter.ios/budgetmeter_iosApp.swift`, line 36), when entering background (`BackgroundProcessingService.swift`, lines 190-195), and it processes pending recurring transactions again when returning foreground (lines 197-202). No UI action is required for foreground/background automation once records exist.

The direct creation of `RecurringTransaction` records may already be partly gated elsewhere, but that does not eliminate the risk:

- Existing users may have records created before Phase 7.
- Restored/imported data can contain recurring transactions.
- Debug/test or future navigation paths can instantiate `RecurringTransactionsView`.
- The view model's manual processing path is exposed through pull-to-refresh if the recurring transactions screen is reachable.

The current background implementation also creates legacy-looking `FinancialCategory` rows with `frequency = "recurring"` (lines 114-124), while the view model path creates one-time automation artifacts with metadata. That is separate from the premium gap but increases the blast radius of unguarded background automation.

### Fix approach

Use the existing service-level premium guard pattern from `DataExportService.exportData(...)`:

```swift
let canProcessRecurringAutomation = await MainActor.run {
    PremiumManager.shared.hasAccess(to: BudgetMeterCapability.recurringAutomation)
}
guard canProcessRecurringAutomation else {
    print("BackgroundProcessingService: Recurring automation skipped; premium required")
    return
}
```

Best location:

- Add the guard at the top of `BackgroundProcessingService.processRecurringTransactions()` before fetching `RecurringTransaction` rows. This covers both `handleBackgroundTask(_:)` and `applicationWillEnterForeground()` because both call the same method.

Recommended related hardening:

- Add the same gate to `RecurringTransactionsViewModel.processDueTransactions()` before it loops due transactions, because `.refreshable` calls it directly.
- Consider gating creation/update of `RecurringTransaction` records in `RecurringTransactionsViewModel.addRecurringTransaction(...)` and `updateRecurringTransaction(...)` if those screens are meant to be entirely premium.
- Align `BackgroundProcessingService.createTransactionFromRecurring` with `RecurringTransactionsViewModel.createTransactionFromRecurring` so background-created entries use the same one-time metadata instead of `frequency = "recurring"`.

## Recommended implementation order

1. Gate `BackgroundProcessingService.processRecurringTransactions()` first. It is the highest-risk leak because it can mutate financial data automatically without the user opening the recurring transactions UI.
2. Gate `RecurringTransactionsViewModel.processDueTransactions()` next, because it is the same automation behavior via manual refresh.
3. Gate the Expense screen `subscriptionsSection` and its add/edit actions.
4. Harden `ExpenseViewModel.loadSubscriptions()` so the locked screen does not load subscription rows/totals for free users.
5. Review summary behavior for subscriptions and recurring transactions to decide whether premium-only sources should be included in free-user financial totals or only hidden from management UI.
